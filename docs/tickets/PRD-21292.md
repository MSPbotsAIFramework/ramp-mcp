## Product design

### Goals / Non-goals

**Goals**: ship a v1 `ramp-mcp` MCP connector exposing **read-only** tools over Ramp's core Accounting & Finance data — card/ACH transactions, physical/virtual cards, users, reimbursements, AP bills, and vendors — so any MCP-compatible agent connected through the MSPbots Agent platform can query a tenant's live Ramp data with that tenant's own Ramp credentials, fulfilling the ticket's literal ask ("live access ... every action logged" — logging/audit is satisfied by the platform's own Gateway-level logging of every tool call, not something this connector adds on top).

**Non-goals (v1)**:
- Write/mutating tools (create or hold a bill, suspend/create a card, hold/release a vendor, submit a reimbursement, link a purchase order, etc.). The ticket's ask is "access," not a named write workflow; starting read-only keeps the blast radius low for a connector that has never been run against a real Ramp account. See Tech design §7 for the full follow-up list.
- A standalone departments/locations lookup tool. Department and location names are already embedded on transaction, user, and card payloads (`card_holder.department_name` etc., seen in the OpenAPI example for `GET /developer/v1/transactions`), which covers the "who/where" questions an agent is likely to ask; a dedicated listing tool is deferred.
- Full PAN / sensitive card-detail retrieval (`POST /developer/v1/vault/cards`, `GET /developer/v1/vault/cards/{id}`) — deliberately excluded so this connector never has to carry card-number-equivalent data.
- Webhooks, vendor agreements, purchase orders, custom accounting records — Ramp exposes ~189 operations in total; v1 covers the 7 read resources above (Tech design §4), the rest is explicitly out of scope until a ticket names a concrete need.

### Acceptance criteria

- **AC1 (discovery)**: Given valid `X-Ramp-Client-Id` / `X-Ramp-Client-Secret` headers, When the agent calls `tools/list`, Then it receives exactly the 7 v1 tools (`ramp_list_transactions`, `ramp_get_transaction`, `ramp_list_cards`, `ramp_list_users`, `ramp_list_reimbursements`, `ramp_list_bills`, `ramp_list_vendors`) with name/description/parameter schema; `GET /health` returns `200 {"status":"ok"}` independent of Ramp's own availability.
- **AC2 (missing credentials)**: Given a `POST /mcp` request missing either required header, When any tool is called, Then the server returns `401` before any call reaches Ramp, and the body names the missing header(s).
- **AC3 (list transactions, filtered)**: Given valid credentials, When `ramp_list_transactions` is called with `from_date`/`to_date` and optionally `department_id`, `user_id`, `card_id`, `min_amount`, `max_amount`, `state`, Then it returns only transactions matching every supplied filter, each record including id, amount, currency, state, merchant, card-holder name/department, and accounting categories.
- **AC4 (pagination)**: Given any v1 list tool's result has more rows than one page, When the agent re-calls the same tool passing the opaque cursor returned as the previous page's `next_cursor`, Then it receives the next page with no duplicate or skipped records, and `next_cursor` is `null` on the last page.
- **AC5 (transaction detail / not-found)**: Given a valid `transaction_id`, When `ramp_get_transaction` is called, Then it returns the full transaction record; given an id Ramp does not recognize, Then it returns a structured `not_found` error, not an unhandled exception.
- **AC6 (cards by type)**: Given `card_type: "physical"` or `"virtual"`, When `ramp_list_cards` is called, Then it calls the matching Ramp endpoint (`/cards/physical` or `/cards/virtual`) and returns only cards of that type, each including card id, display name, holder user id, and activated/terminated state.
- **AC7 (users / reimbursements / bills / vendors listings)**: Given valid credentials and the resource's own optional filters (email/department/location for users; state/date range/user for reimbursements; vendor/status/date range for bills; name/active for vendors), When the corresponding tool is called, Then it returns only matching records with the fields needed to answer "who / what / when / how much" about that resource, honoring pagination (AC4).
- **AC8 (upstream error passthrough)**: Given Ramp responds `400`/`401`/`403`/`404`/`429`/`5xx` to any proxied call, When the tool call completes, Then the connector returns a structured error envelope (`code`, `message`, Ramp's `x-trace-id` when present) instead of crashing or leaking a raw stack trace; a `429` is surfaced as `code: rate_limited`, not silently retried.
- **AC9 (per-tenant isolation)**: Given two tool calls arrive concurrently carrying two different `X-Ramp-Client-Id`/`-Secret` pairs, When both execute, Then each caller receives only the data its own Ramp credentials are authorized for, and no cached access token or response data from one call is ever used to answer the other.
- **AC10 (README contract)**: Given the delivered repo, When `README.md` is read, Then it documents what the product is, the required Header table (`X-Ramp-Client-Id`, `X-Ramp-Client-Secret`) with where to obtain them, the v1 tool table, and a "MSPbots Connector" promo paragraph matching `vendor-mcp-development` skill's `reference/readme-connector-section.md` verbatim.

## Tech design

### Conclusion

Build the first version of `MSPbotsAIFramework/ramp-mcp` from scratch (today it is an empty scaffold — just a two-line README) following the `vendor-mcp-development` SOP's primary line A: Python, FastMCP over Streamable HTTP, the SOP's standard module shape (`server.py` + `api_client.py` + `tools/<resource>.py`). Credentials come only from the `X-Ramp-Client-Id` / `X-Ramp-Client-Secret` headers (SOP §3.1); the connector exchanges them for a Ramp OAuth2 `client_credentials` access token via `POST /developer/v1/token` and caches that token in-process keyed by `sha256(client_id:client_secret)` with TTL = `expires_in` minus a safety buffer — this follows both the SOP §3.4 exception (cache allowed when the key carries a credential fingerprint and an expiry) and Ramp's own guidance to reuse tokens rather than hit its separately-rate-limited token endpoint on every call. All 7 v1 tools are read-only `GET`s against Ramp's Developer API v1.

### Data & API contract

**Header credentials** (declared in README per SOP §3.1):

| Header | Required | Meaning | Where to obtain |
|---|---|---|---|
| `X-Ramp-Client-Id` | Yes | OAuth app Client ID | Ramp Developer Portal → API connections → your app |
| `X-Ramp-Client-Secret` | Yes | OAuth app Client Secret | same place |

No `X-Ramp-Base-Url` — Ramp's OpenAPI spec lists a single production server (`https://api.ramp.com`); there is no self-hosted or sandbox host to switch between.

**Token exchange**: `POST https://api.ramp.com/developer/v1/token`, `Content-Type: application/x-www-form-urlencoded`, `Authorization: Basic base64(client_id:client_secret)`, body `grant_type=client_credentials&scope=transactions:read users:read cards:read reimbursements:read bills:read vendors:read` (scope list is a fixed code-level constant matching exactly the 7 v1 tools — narrower than Ramp's 60+-scope catalogue, least-privilege). Response: `access_token`, `expires_in` (OAuth2 client_credentials standard shape; Ramp's own `TokenRequestBody`/response schemas were read from `openapi/developer-api.json` components but the response schema name was not dumped this round — dev should pull it directly from the already-fetched spec file instead of guessing field names, see §10 "Main uncertainty"). Cached per `sha256(client_id:client_secret)` with TTL = `expires_in − 60s`.

**Tool → Ramp endpoint mapping** (all `GET`, `Authorization: Bearer <access_token>`):

- `ramp_list_transactions` → `GET /developer/v1/transactions` (`transactions:read`)
- `ramp_get_transaction` → `GET /developer/v1/transactions/{transaction_id}` (`transactions:read`)
- `ramp_list_cards(card_type)` → `GET /developer/v1/cards/physical` or `GET /developer/v1/cards/virtual` (`cards:read`)
- `ramp_list_users` → `GET /developer/v1/users` (`users:read`)
- `ramp_list_reimbursements` → `GET /developer/v1/reimbursements` (`reimbursements:read`)
- `ramp_list_bills` → `GET /developer/v1/bills` (`bills:read`)
- `ramp_list_vendors` → `GET /developer/v1/vendors` (`vendors:read`)

**Pagination**: Ramp returns `{data: [...], page: {next: "<full URL with cursor params>"|null, total_count, total_count_capped}}` (OpenAPI schemas `DeveloperAPICountedPage` / `CountedPaginatedResponseApi*`, confirmed 2026-11-02 from the fetched spec's `components.schemas`). Tools expose this to the agent as `{items: [...], next_cursor: <opaque cursor extracted from the query part of `next`>|null}` so the agent never has to parse or reconstruct a full URL.

**Errors**: Ramp returns `{error_v2: {...}}` on 4xx (`DeveloperApiErrorResponse`/`DeveloperApiError` schemas) plus an `x-trace-id` response header. Tools map this to `{error: {code, message, trace_id}}` with `code` ∈ `unauthorized` (401) / `forbidden` (403) / `not_found` (404) / `invalid_input` (400/422) / `rate_limited` (429) / `upstream_error` (5xx) / `not_configured` (credentials absent at the tool layer — defensive only; the live path already 401s in middleware per SOP §3.2 before reaching a tool).

**Backward compatibility**: n/a — brand-new connector, no existing consumers.

### Non-functional

- **Idempotency & concurrency**: every v1 tool is a `GET`, naturally idempotent — no duplicate-side-effect concerns from retries. Concurrent requests from different tenants are isolated by the `ContextVar` middleware (SOP §3.3); the token cache key includes the credential pair, so two tenants never share a cached token.
- **Performance**: list tools pass the agent's `page_size`/`cursor` straight through to Ramp rather than fetching every page and filtering client-side (avoids pagination storms on large businesses). Token caching turns steady-state calls into one `GET` instead of a `POST /token` + `GET` pair, which also keeps well under Ramp's separate 100 req/10s/IP token-endpoint cap.
- **Security**: credentials never touch disk, env vars, or logs (SOP §3.1/§6); access tokens are likewise never logged; `gitleaks detect` run before delivery (SOP §11); full PAN / sensitive card-detail endpoints are excluded from v1 scope entirely (Non-goals) so the connector never has to handle card-number-equivalent data.
- **Multi-tenant isolation**: the request-scoped `ContextVar` carries the credential pair end-to-end with no module-level or global API client instance; the token cache key is derived from the credential pair, so a cache hit can never serve tenant A's token to tenant B's request.
- **Observability**: log tool name, Ramp HTTP status, `x-trace-id`, and latency per call — never credentials or response bodies; log a `429` at warn level since it signals the shared-IP rate limit is close.

### Decisions made by DEV01

(No one to ask for a brand-new connector with a generic ticket ask — these are the first-version choices and their alternatives, per `mcp-track.md` §2.4.)

- **v1 scope = 7 read-only tools, no write/mutating tools.** Alternative: cover some of Ramp's write endpoints (create bill, suspend card, etc.) now. Rejected — ticket says "access," names no write workflow, and read-only keeps risk low for an unexercised connector (see Option analysis).
- **No standalone departments/locations tool.** Alternative: add dedicated `ramp_list_departments`/`ramp_list_locations` tools now. Deferred — the names are already embedded on transactions/users/cards, which should cover the common questions; a real follow-up need is a small, separate ticket.
- **Access token cached in-process, keyed by `sha256(client_id:client_secret)`, TTL = `expires_in − 60s`.** Alternative: never cache, re-exchange a token on every tool call. Rejected — Ramp's own docs recommend reusing tokens and rate-limit the token endpoint separately (100 req/10s/IP); caching keyed by the credential pair stays inside the SOP §3.4 exception (fingerprinted key + expiry) without weakening per-tenant isolation.
- **Cards unified into one `ramp_list_cards(card_type: "physical"|"virtual")` tool** instead of two separate tools. Alternative: `ramp_list_physical_cards` + `ramp_list_virtual_cards` as two tools. Chosen to cut the v1 tool count while keeping a clean 1:1 mapping to Ramp's two card endpoints via the parameter.
- **No `X-Ramp-Base-Url` header.** Alternative: add one for symmetry with connectors that do support self-hosted instances. Rejected — Ramp's OpenAPI spec lists a single production host; there is nothing to point it at.
- **OAuth `scope` requested at token-exchange time is a fixed code-level constant** (the 6 read scopes needed by the 7 tools), not something the caller can override via a header. Alternative: let the caller pass custom scopes. Rejected — keeps the credential surface to exactly 2 headers (SOP: one credential per Header, no packed values) and applies least-privilege against Ramp's 60+-scope catalogue.
